# Atlas CAN：2バスの帯域余裕とCAN FD案

2026-11-18。**計算による設計比較・未実装・実バス負荷未測定**。
通常動作の要求とClassic ID案は[CAN詳細](atlas_can.md)、FD用の追加候補は[FD ID一覧](atlas_can_fd_ids.csv)。
今回の前提はユーザー指定の2バス構成であり、Mainだけが両バスに接続する。FDについてはユーザー指定により、**同居するC610/電源がFDを妨害せず通信可能である前提**で比較する。

## 1. バス構成と計算条件

```text
             ┌ Bus A ─ ステア基板1台（2軸）＋ C610×2
Main ────────┤
             └ Bus B ─ ステア基板1台（2軸）＋ C610×2 ＋ 電源基板
```

A/Bは説明用の名前で、MainのFDCAN1/2やboard_id=0/1への対応は今回確定しない。
両バスの負荷を足して1 Mbpsと比較しない。MainのCPU/RX処理量は両バスの合計で評価する。
通常のセンサーや指令をMainが反対側へ無条件に中継することは想定しない。共通エラーの橋渡し・重複抑止は別途定義する。

| 項目 | 今回の条件 | 確定状態 |
|---|---|---|
| nominal rate | 各バス1 Mbps、標準11 bit | 既存Classic条件を維持 |
| C610帰還 | 1台1 kHz、各バス2台、DLC8 | メーカー既定値。実機設定は未読出し |
| C610指令 | 各バス1つのグループID、500 Hz、DLC8 | 500 HzはMain制御周期に合わせた比較仮定。1 kHzも別計算 |
| ステア高速 | 指令・角度・電流を各100/250/500 Hz | ユーザー指定の100〜500 Hz内で比較 |
| 中速 | 基板制御1本＋2軸の制限値、各10 Hz | 合意済み。変更時の追加送信は別枠 |
| 温度 | 2軸、各1 Hz | 合意済み |
| 電源基本例 | DLC8換算で90フレーム/秒 | 仮定：電圧2種・温度・電流を各20 Hz＋Main生存通知10 Hz |
| 電源マウス例 | 上記にDLC8・1 kHzを追加 | 旧Atlas CSVの0x241周期を含めた感度分析。現在の実送信量は未測定 |
| 校正・構成 | 項目数未定のため基本表では除外 | 約1秒周期送信は維持。決定後に必ず加算 |

C610は2台を同じ4台グループに入れ、1本の電流指令へまとめる。別グループなら指令が2本になる。
C610の500 Hz指令を1 kHzにすると各バスに6.75ポイント加算される。2グループを各500 Hzで送る場合も同じ増分である。
ロボット全体でID重複を避ける例として、AのC610を1/2、Bを5/6とすれば、指令0x200/0x1FF・帰還0x201/202/205/206を分離できる。これは配置候補であり確定ではない。
1/2と3/4を別バスへ置く場合はグループ指令ID0x200が両バスで同じになるため、Mainはバス別payloadで扱う。C610固定IDをステアの予約へ転用しない。

Mainの現在の`power_board.c`は電源指令を両バスへ送るAPIである。表は新しい物理配置に合わせBだけへ送る想定であり、従来どおりAにも10 Hz送るならAに0.135ポイント追加する。
電源側の周期を変更する提案ではない。既存設定の読出しまたはCAN観測で実量を確定する。

## 2. フレーム時間のモデル

ClassicのD byte標準データフレームはIFS込みで、無スタッフ長`47+8D` bit、SOF〜CRC列の最大スタッフ数の見積り`floor((33+8D)/4)`を加える。
1 MbpsではDLC4=95 µs、DLC8=135 µs。実データのスタッフ数が少なければこれより短い。

FDは任意データでの厳密なISOフレーム長計算ではなく、比較用の余裕を含む工学的概算として
`T_fd(D) = 40/nominal_Mbps + ceil(1.25 × (8D + 50))/data_Mbps [µs]`
を使用する。調停/終端40 bit、データ/CRC等50 bitの枠とスタッフ余裕を含む。1/2 Mbpsは調停1 Mbps・データ2 Mbpsの意味。
規格の正確なフィールド/スタッフ数やビットレート切替点を模擬した上限保証ではない。採用後は実際のpacket形式・波形で再計算/計測する。

| FD payload | 1/1 Mbps、BRSなし相当 | 1/2 Mbps | 1/4 Mbps |
|---:|---:|---:|---:|
| 12 byte | 223 µs | 131.5 µs | 85.75 µs |
| 20 byte | 303 µs | 171.5 µs | 105.75 µs |
| 32 byte | 423 µs | 231.5 µs | 135.75 µs |
| 64 byte | 743 µs | 391.5 µs | 215.75 µs |

エラー再送・bus-off復帰・変更時burst・ACK再試行は含めない。平均使用率だけで指令の最大遅延を保証しない。

## 3. 現在のClassic分離案：各バスの使用率

1バスのステア2軸で、指令DLC4×2、電流DLC4×2、角度/角速度DLC8×2を1周期に送るため、1周期650 µs相当。
C610帰還2台×1 kHzは27%、グループ指令500 Hzは6.75%、合計33.75%が固定負荷となる。

| ステア各高速レート | A：電源なし | B：電源基本例 | B：電源＋マウス1 kHz例 |
|---:|---:|---:|---:|
| 100 Hz | 40.67% | 41.89% | 55.39% |
| 250 Hz | 50.42% | 51.64% | 65.14% |
| 500 Hz | 66.67% | 67.89% | 81.39% |

いずれも校正・構成・変更時追加送信は別。
電源基本例は1.215ポイント、マウス1 kHz例はさらに13.5ポイントを追加する。電源側に他の周期データがあれば同様に加算する。
C610指令も1 kHzの場合、500 HzステアではA=73.42%、B基本=74.64%、Bマウス込み=88.14%になる。

**2分割によりClassicの100〜250 Hzには検討余地があるが、500 Hzを全項目へ適用すると電源側の余裕が小さい。**
一律に周期を落とす前に、電源/マウスの実レートとC610指令周期を確定することが有効である。

## 4. FD案：基板内2軸を一括送信

別バスの4軸を1フレームにしない。各基板内の2軸を1フレームへまとめる。
角度とDutyは動作モードに応じた一方だけを送信する。

| 用途 | board_id=0 / 1のID候補 | 形式 | 周期 | payload案 |
|---|---|---|---|---|
| 2軸角度指令 | 0x124 / 0x125 | FD 12 byte | 100〜500 Hz | header4 byte＋M0/M1 float32 rad |
| 2軸Duty指令 | 0x134 / 0x135 | FD 12 byte | 100〜500 Hz | header4 byte＋M0/M1 float32比率 |
| 2軸角度・電流帰還 | 0x254 / 0x255 | FD 20 byte | 100〜500 Hz | header4 byte＋各軸の角度float32/電流float32 |
| 2軸電流・Duty制限 | 0x334 / 0x335 | FD 20 byte | 10 Hz＋変更時 | header4 byte＋各軸の電流上限float32/Duty上限float32 |
| 基板制御 | 0x350 / 0x351 | Classic 8 byte | 10 Hz | 既存候補を継続。payload未定義 |
| 2軸温度 | 0x294 / 0x295 | FD 12 byte | 1 Hz | header4 byte＋各軸温度float32 |
| 校正パラメーター一式 | 0x604 / 0x605 | FD 最大64 byte | 一式を約1 Hz | 基板内の軸・世代・分割indexをheaderで識別。データ部最大56 byteの案 |
| 構成パラメーター | 未定 | 未定 | 1 Hz | 項目集合・IDは別途定義 |
| 共通エラー | 0x000 | Classic 8 byte | 事象時 | 電源互換の既存形式を維持 |

header4 byteはsequence uint16、軸ごとのvalidを含むflags、形式版等を置く候補であり、bit割当は未定義。
動作モード・プロトコル版を明示し、Classic分離案とFD一括案を同時に定期送信しない。
新IDは既存の軸別IDや既存更新予約と重複しない候補として分離した。採用はまだ決定していない。
IDで基板を特定し、payload内のM0/M1順は固定する。受信の一括検証に失敗したときの両軸の扱い、更新時刻、受信期限も実装前に定義する。

最小帰還20 byteはユーザー要求の角度・電流を含む。既存候補の角速度も高速で維持する場合は、各軸にfloat32角速度を追加して32 byteへ拡張する（28 byteはFDの有効長にない）。
この拡張を使うかは未確定であり、20/32 byteを受信側との合意なしに切り替えない。
校正一式の約1 Hz・無要求送信は維持し、FDを使うことを理由に要求式へ変更しない。

## 5. パケット集約の比較

各バスのステア高速500 Hz、C610指令500 Hz、帰還1 kHz。中低速も各方式のpayload時間で計算する。

| 方式 | A | B基本 | Bマウス込み | 内容 |
|---|---:|---:|---:|---|
| Classic分離（現案） | 66.67% | 67.89% | 81.39% | 指令4 byte×2、電流4 byte×2、角度/速度8 byte×2 |
| Classic最小帰還集約 | 57.17% | 58.39% | 71.89% | 各軸の角度＋電流を8 byteへ。高速角速度を含まない |
| FD 1/1 Mbps | 60.51% | 61.73% | 75.23% | 2軸指令12 byte＋帰還20 byte。BRSなしでは改善は限定的 |
| FD 1/2 Mbps | 49.22% | 50.43% | 63.93% | 2軸指令12 byte＋帰還20 byte |
| FD 1/4 Mbps | 43.57% | 44.79% | 58.29% | 同上 |
| FD 1/2 Mbps＋角速度 | 52.22% | 53.43% | 66.93% | 2軸帰還32 byte。現案の高速角速度を維持 |

角速度の有無が異なるため、最小帰還案と現案は全データが同一ではない。100/250 Hzの値も計算スクリプトで出力する。
FD 1/2 Mbps・250 Hzなら、A=41.64%、B基本=42.86%、Bマウス込み=56.36%。C610指令1 kHzでは各値に6.75ポイント加算される。
500 Hzが必要ならFD 1/2または1/4 Mbpsを候補とし、まず250 Hzから校正/構成の追加分と遅延を検証する案を推奨する。
この推奨は今回の仮定下の設計判断であり、100〜500 Hzという要求範囲を変更する決定ではない。

## 6. 校正・構成データと瞬間負荷

基本表は未定の一式サイズを0としている。Classicのデータ部4 byte/フレーム、FD64のデータ部56 byte/フレームという候補で、1軸K byteの校正を1 Hzで送ると、1バスの追加時間は次の概算となる。

- Classic：`2 × ceil(K/4) × 135 µs/s`。
- FD 1/2 Mbps：`2 × ceil(K/56) × 391.5 µs/s`。

開始/終了・CRC・世代などの追加フレームが別途必要ならその分も加算する。
K=512 byteを例にするとClassicは約3.456ポイント、FDは約0.783ポイントを追加する。旧案の「LUT1要素=1フレーム」ならさらに増える。
構成パラメーターは同一バスあたり毎秒Cフレーム、全てClassic DLC8で見込むなら`0.0135 × C`ポイントを加算する。

低優先のFD64でも、送信開始後は上位IDのフレームが割り込めず、今回の1/2 Mbpsモデルでは1本約391.5 µsを占有する。
校正一式を1秒ごとに一斉burst送信せず、2軸の開始時刻を分散し、各周期内で平準化する。Main/ステアのTXキューは最新値を優先し、低速データの滞留で高速指令を遅延させない。
使用率100%未満だけで合格とせず、設計上は平均60%程度以下を初期目安として追加・再送・burstの余裕を取り、最終的には最悪遅延を測定して判断する。この60%は本検討の目安であり規格値ではない。

## 7. FDの適用前提と実装差

ユーザー指定により本比較ではFDが同居バスで使用可能と仮定する。これはC610/電源のFD耐性の実証ではない。
IDが相手の受信フィルター外でも、ClassicコントローラーがFDをエラーと解釈する問題は回避できない。
将来の結合確認で前提が成立しない場合、電源FWを変更して回避せず、Classic集約案または物理的なFD分離/ゲートウェイを再検討する。

ステアの保存回路資料はMAX3051で、公称上限1 Mbps。2/4 Mbpsの採用時は現物の型番・変更履歴・配線・終端・伝搬を確認する。
1/1 MbpsのFDでもプロトコル耐性の確認は必要である。両端MCUがFDCANを持つことだけではバス全体のFD対応を保証しない。
Mainの現在の`board_can_frame_t`/送信APIは8 byteのClassic用で、ステアもClassic設定・8 byte境界である。FDのDLC、最大長、FDF/BRS、Message RAM、フィルター、エラーハンドリングを実装時に見直す。

## 8. 再計算

MainFWルートから実行する。実機通信は行わない。

```powershell
python Script/estimate_atlas_can.py
python Script/estimate_atlas_can.py --c610-command-hz 1000
python Script/estimate_atlas_can.py --calibration-bytes-per-axis 512 --configuration-fps 4
python Script/estimate_atlas_can.py --c610-command-groups 2 --csv
```

校正byte数/構成fpsが0なら未定義分を除外する意味であり、実際に送信しない仕様へ変更したことではない。
実バスでのID/DLC/周期、使用率、変更時burst、C610帰還のジッター、停止遅延、RX drop/エラー再送を確認して計算条件を更新する。
